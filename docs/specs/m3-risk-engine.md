MediFlow AI — Module 3 Architecture (Risk
Engine)
Module 3 predicts which patients will miss their follow-up appointment, gives each
appointment a risk score with a plain-language reason, and hands the high-risk list to
Module 4 for reminders. Each section below can be handed to a coding agent as-is.
Flow at a glance
Training builds and saves one model. Every appointment created from an approved
Module 1 note is then scored by that saved model, explained with SHAP and one LLM
sentence, and placed on the risk list Module 4 reads.
Role in the product
Module 3 decides who needs a reminder. A missed follow-up means an unfinished
treatment for the patient and an empty slot for the clinic; this module finds those patients
before it happens.

Scope for the prototype: one model, no-show prediction. Readmission risk is left for a
later version because no-show links directly to Module 4 and is easy to explain and
measure.
Connections
From Module 1: when a doctor approves a note with a follow_up_date, an appointment
is created. That appointment is scored automatically.
To Module 4: the scored list, sorted by risk, is what the Patient messenger uses to
decide who gets a reminder and how many.
To Module 5: the Care coordinator calls the scoring endpoint as a tool when planning a
patient's next steps.
On screen: a "Upcoming appointments" page shows each appointment with its risk
band and a one-sentence reason.
Target and features
Target variable: no_show : 1 if the patient missed the appointment, 0 if they attended. This
is binary classification. The model outputs a risk score from 0 to 1 for each appointment.
Features: 10, all known before the appointment day.

Columns in the CSV that are NOT features: appointment_id, patient_id,
appointment_date. They identify rows; feeding them to the model would let it memorise
rather than learn.
Leakage rule: a feature is only allowed if it is known when the appointment is booked.
Anything known only on or after the day (cancellation calls, check-in time, rescheduled
flag) is excluded, because it gives away the answer and makes the model look better in
testing than it would be in real use.
Synthetic data design
The data is generated by a seeded Python script, not an LLM: an LLM cannot produce
5,000 rows with consistent statistical relationships, but a script can. Output is a clean
CSV, no missing values.
How the target is created
1. Generate the 10 features for each row from realistic distributions.
2. Compute a hidden risk number (log-odds) from the features using fixed rules (below).
3. Add random noise, so the model can learn the pattern but never reach a perfect score.
4. Turn it into a probability (sigmoid) and draw no_show as 1 or 0 from that probability.
5. Adjust the base value so about 20% of rows are no-shows.

Training pipeline
Runs once with python ml/train_no_show.py , and again whenever the data changes.
Random seed 42 everywhere so results are reproducible.
C1. Load and check
Load data/ml/appointments.csv .
Check: expected columns present, no missing values, values inside the ranges in Target
and features, previous_no_shows never above previous_visits , no-show rate
between 15% and 25%. Stop with a clear error if any check fails.
C2. Preprocess
One-hot encode sex , day_of_week , visit_type (one column per value).
Scale numeric features with StandardScaler for logistic regression only. XGBoost uses
trees, which split on thresholds and don't care about scale.

Wrap preprocessing and model together in one scikit-learn Pipeline with a
ColumnTransformer . Why: the exact same transformation is then applied at scoring
time, so a new appointment is never encoded differently from the training data.
C3. Split
80% train, 20% test, stratify=no_show . Why stratify: both sets keep the same ~20%
no-show ratio, so the test score is fair.
The test set is not touched until final evaluation.
C4. Baseline: logistic regression
LogisticRegression(class_weight="balanced", max_iter=1000) .
Why a baseline: it is simple and explainable, and it sets the score XGBoost must beat. If
the complex model can't beat the simple one, the complexity isn't worth it.
C5. Main model: XGBoost
XGBClassifier with scale_pos_weight = (number of 0s) / (number of 1s) in the
training set, about 4.
Why scale_pos_weight: with only 20% no-shows, a model can reach 80% accuracy by
predicting "everyone comes" and catch zero no-shows. Weighting each no-show about
4 times makes missing one cost as much as the whole majority, so the model actually
learns to find them. It is XGBoost's equivalent of class_weight="balanced" .
Small tuning grid with 5-fold stratified cross-validation on the training set, scored by
AUC: max_depth 3, 4, 5; n_estimators 200, 400; learning_rate 0.05, 0.1. That's 12
combinations, which is enough for a prototype.
Why XGBoost: it is the strongest standard choice for table-shaped data, handles
mixed feature types, and works directly with SHAP for explanations. Random forest is
skipped because XGBoost usually does the same job better.
C6. Evaluate and pick
Score both models on the test set: AUC, precision, recall, confusion matrix.
Ship XGBoost only if its AUC beats the baseline's. If it doesn't, ship the baseline and
note it in the model card.
Accuracy is not used to choose, because on imbalanced data it rewards predicting
"everyone comes".
C7. Save
Save the whole pipeline to models/no_show/v1/model.joblib .
Save metrics.json , the feature list, and plots (ROC curve, precision-recall curve,
confusion matrix, SHAP summary) to the same folder.
Write docs/model-cards/no_show_v1.md : purpose, data, features, metrics, limits.

Scoring and explanation
Runs every time an appointment is created, and once a day for all upcoming
appointments.
C8. Build the feature row
Trigger: a Module 1 note is approved with a follow_up_date, which creates a row in
appointments .
Job: assemble the 10 features for that appointment: age, sex, distance and NHIS status
from the patient record; previous_visits and previous_no_shows from appointment
history; lead_time_days, day_of_week, rainy_season and visit_type from the
appointment itself.
C9. Score
Load the saved pipeline once at startup and call predict_proba .
Bands: High ≥ 0.50, Medium 0.25–0.49, Low < 0.25.
C10. Explain with SHAP
Use shap.TreeExplainer on the XGBoost model.
Take the 3 features with the largest positive SHAP values (the ones pushing the risk
up), with their actual values. Example: previous_no_shows=2 (+0.9) ,
distance_km=38 (+0.5) , lead_time_days=30 (+0.3) .
C11. Turn it into one sentence (LLM)
Claude writes the sentence the nurse sees. Prompt stored as
prompts/risk_explain_v1.txt :
Write one sentence (under 30 words) for a clinic nurse explaining why
this appointment has a {band} risk of being missed.
Use ONLY these factors, in this order of importance. Do not add any
other reason, and do not mention numbers like SHAP values.
{top_factors_with_values}
Use plain words: "has missed 2 of her last 4 visits",
"lives about 38 km away", "was booked 30 days ahead".
Do not give medical advice. Do not use the patient's name.

KPIs and evaluation
All KPIs are measured on the 20% test set (about 1,000 appointments) and written to
metrics.json and the model card.
Precision vs recall trade-off: missing a no-show (low recall) costs a lost visit; a wasted
reminder (low precision) costs one SMS. So recall matters slightly more here, which is why
its target is higher.
Interview line: on synthetic data these scores reflect the rules we built. The point is the
pipeline: on real hospital data it retrains unchanged, and the numbers become a true
measure.
